## Summary

Advances this repo's two stale pins **and the charly pin they now require**. Those cannot be
separated: with the pins advanced but charly left at `v2026.238.1242`, validation fails
because the newer `pod-waybar` reached transitively through `pod-wayvnc` uses schema that
charly cannot parse.

Pins advanced:

```
  layer-sway-desktop    v2026.242.1839 -> v2026.243.0831
  pod-wayvnc            v2026.237.559  -> v2026.243.0508
  charly (deploy.yml)   v2026.238.1242 -> v2026.240.2035
```

The candy's **own** CalVer stamp advances with them, `charly.yml:3`:

```
  version (this candy)  2026.242.1845  -> 2026.243.0835
```

That is the fourth changed version value in the diff, and it is required rather than
cosmetic: the pins above change what this candy resolves to, so the changed content must
ship under a new version instead of being republished under an already-released one. An
earlier revision of this body listed only the three pins and omitted this stamp — the
accounting is now complete against `git diff`.

`v2026.240.2035` is not a guess: it is the charly pin the sibling `layer-sway-desktop` landed
on when it hit this same `pod-waybar` coupling, and it is verified below rather than inherited
on faith.

A published tag embeds the pins it carried at tag time, so consumers pinning a tag of this
candy drag its old refs into their own resolution and charly reports `resolved to multiple
versions` on every build. Part of an ordered org-wide sweep (opencharly/distro-cachyos#48);
the scan is now down to 7 repos / 16 stale pins, from 93 / 188 when it started.

## How tested

`charly box validate` run from the committed tree with the **v2026.240.2035** binary this PR
pins — not a newer one, which would prove nothing about the pin actually being landed:

```
$ /tmp/claude-1000/charly240/bin/charly box validate
$ echo $?
0
```

The exit code is read from charly directly, never through a pipe — a piped `| tail` reports
the pipe's status, not the command's. The run prints **no output at all** on success: this
charly predates opencharly/plugin-box#7, which is precisely why that change added a summary
line. A silent pass is not quotable evidence, so the exit code is the evidence here.

**Negative control** — the same committed tree validated with the **previously pinned**
`v2026.238.1242`:

```
$ /tmp/claude-1000/charly238/bin/charly box validate
charly: error: command "validate": validation error: candy "github.com/opencharly/pod-waybar":
  CUE schema: .../pod-waybar@v2026.243.0508/charly.yml: candy "waybar": 2 errors in empty disjunction:
    distro: conflicting values {fedora:{package:["waybar"]}} and [...(string & !="")]
            (mismatched types struct and list)
    service.0.wait_for: field not allowed
$ echo $?
1
```

Both diagnostics are schema-version skew, not authoring errors: the newer candy uses the
`distro:` map form and `service.wait_for`, which `v2026.238.1242` predates. This control is
the proof the charly bump is load-bearing rather than incidental — the pin advance does not
validate without it.
