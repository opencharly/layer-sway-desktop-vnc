# 2026.242.1906 — chore: advance the layer-sway-desktop pin to v2026.242.1839

## Summary

`layer-sway-desktop` fixed four stale pins that declared dependencies as **bare names**
instead of full `@github` refs (opencharly/layer-sway-desktop#3), taking its own
`charly box validate` from exit 1 to exit 0.

This repo still pinned `v2026.238.2103`, which predates that. Left alone it drags the old
transitive pins of `layer-xdg-portal` and `layer-chrome-sway` back into any project that
composes this candy, which charly reports on every build:

```
Warning: candy github.com/opencharly/layer-xdg-portal resolved to multiple versions;
using newest 2026.242.1655 (from …@v2026.242.1648), ignoring 2026.144.1443 (from …@v2026.237.557)
```

**Measured, not assumed.** In a downstream project, the count was 0 before any consumer
pinned `layer-xdg-portal`, 3 after one did, and still 3 after repinning every *direct*
consumer — which identified the survivors as transitive. After repinning
`layer-sway-desktop` itself to `v2026.242.1839`, the remaining old refs were attributed
specifically to `layer-sway-desktop@v2026.238.2103`, i.e. this pin.

## How tested

```
$ charly box validate
exit 0
```

Run with charly **`v2026.238.1242`**, the version this repo's `deploy.yml` clones and
builds, so it is the same gate CI runs rather than a newer local binary. The exit code was
read directly from `charly box validate`, not through a pipeline.

The consuming project's zero-warning bed run lands with the repin that follows this tag —
the same ordering constraint that applied to `layer-sway-desktop#3`: a transitive pin can
only stop being resolved once the repo removing it is merged and tagged, so no bed run in
*this* repo can demonstrate the drop.
